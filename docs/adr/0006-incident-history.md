# ADR-0006: Incident history (the agent's memory)

- **Status:** Accepted
- **Date:** 2026-11-09

## Context

Alerts are transient: Prometheus forgets them when they stop firing, and Prometheus and Loki in the cluster use `emptyDir` storage (ADR-0005). The agent needs a durable record of **what broke, when, how fast we noticed, how fast it was fixed and why**, for three reasons:

1. **Measure reliability** with the standard SRE numbers, MTTD and MTTR, before and after the agent exists (Phase 9 compares them).
2. **Give the agent memory**: in Phase 6 it will look up similar past incidents and their root causes when diagnosing a new one.
3. **Build an evaluation dataset**: each drill produces a labeled incident (alerts, logs, known root cause).

## Decision

- **Incidents are built from Prometheus alerts.** A small collector (`centinela collect`) polls `/api/v1/alerts` every 15 s. No Alertmanager: it would only add another container to the 16 GB budget, and the collector needs the full list of firing alerts anyway.
- **Grouping:** one outage fires several alerts (`ServiceDown` on payments, then `UpstreamErrors` and `HighErrorRate` on orders). A new alert **joins the open incident** instead of opening another one; with no open incident it opens a new one. The incident takes the most severe alert, earliest first, as its title. This simple rule is correct for a single-tenant shop; the agent will refine cause vs symptoms in Phase 6.
- **The decision logic is a pure function** (`tracker.plan(firing, open_incidents, now) -> actions`) with no I/O, unit-tested with fixed timestamps. The collector only applies its actions to the store.
- **Definitions:**
  - `started_at` = `activeAt` of the first alert (when the condition began, before the `for:` delay).
  - `detected_at` = when the collector first saw it firing.
  - `resolved_at` = when the **last** alert of the incident stopped firing.
  - **MTTD = detected_at − started_at**, **MTTR = resolved_at − detected_at**.
- **Storage: a separate PostgreSQL** (`incidents-db` in namespace `centinela`, 1 GiB volume), not the shop's database. The system that records outages must not share a failure domain with the system that has them, and the agent will never need credentials to the shop's data. Three tables (`incidents`, `incident_alerts`, `incident_events`) plus a view `incident_metrics`. Schema migrations are idempotent and run when the collector starts.
- **Evidence:** when an alert joins an incident, the collector attaches the last error/warning **logs from Loki** for that service (2 minutes before the alert started) as an `incident_events` row. Best effort: a Loki failure never blocks incident tracking.
- **Postmortem:** `centinela incidents close ID --cause .. --resolution ..` records the root cause. Today a human writes it; in Phase 6 the agent proposes it.
- **Grafana reads, never writes:** a `grafana_reader` role with `SELECT` only. Both passwords are generated by Terraform; the reader password is the only secret copied into the `observability` namespace.
- **Self-observed collector:** it exposes `/metrics` on port 9100 (polls by result, open incidents, firing alerts, incidents created/resolved), scraped by Prometheus.

## Lessons from the first Kubernetes drill

Payments scaled to 0 for 3 minutes (`scripts/incident-drill.sh`). Result: 1 incident, **MTTD 69 s**, MTTR 8.0 min (3 min of deliberate downtime + 4.5 min until every alert cleared).

- **`ServiceDown` never fired.** With zero pods, Kubernetes service discovery removes the target, so `up` *disappears* instead of becoming 0, and `up == 0` matches nothing. The outage was only visible through its symptoms (`UpstreamErrors`, `HighErrorRate`). The rule now also fires for services seen in the last hour that have no `up` series (`max_over_time(...[1h]) unless up`), with a `promtool` test that fails on the old rule. Second drill with the fix: `ServiceDown` was the first alert of the incident and its title became "payments is down" (MTTD 89 s). A production cluster would use kube-state-metrics (`kube_deployment_status_replicas_available == 0`); we skip it to save memory. Classic monitoring trap: **alert on absence, not only on bad values.**
- **A symptom can fire after the fix.** `HighLatencyP95` (5-minute window, `for: 5m`) started firing *after* payments was back, joined the still-open incident instead of opening a new one, and was the last alert to clear. This is why grouping matters and why MTTR includes the clearing lag.
- Timestamps are stored and shown in UTC (`timeline (UTC)` in `incidents show`), the usual convention for incident timelines across time zones.

## Consequences

- **MTTR includes the alert-clearing lag.** Rate-based alerts (`HighErrorRate`) use 5-minute windows, so they keep firing for a few minutes after the fix. First drill: payments down, 1 incident with 3 alerts, **MTTD 64 s, MTTR 3.5 min**, of which roughly 2 minutes were the windows draining. This is the honest number a real alerting system would report; shorter windows would make alerts noisy.
- **Collector downtime inflates MTTD.** If the collector is down when an alert starts, `detected_at` is when it comes back (seen in testing: 2.3 min instead of ~1 min). That is correct: nobody was watching.
- **The `centinela` namespace quota grew** from 512 MiB to 1 GiB: incidents-db (~40 MiB) and the collector (~45 MiB) now, the agent in Phase 6.
- One collector replica only (`Recreate` strategy): two pollers would race to open the same incident. Acceptable for a demo; a production version would use a leader lock (`pg_advisory_lock`).
- Runbooks (`docs/runbooks/`) are linked from every alert (`runbook_url`) and are the knowledge base the agent retrieves from in Phase 6.
