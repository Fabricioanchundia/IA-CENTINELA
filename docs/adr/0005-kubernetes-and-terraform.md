# ADR-0005: Local Kubernetes (k3d) and Terraform

- **Status:** Accepted
- **Date:** 2026-11-09

## Context

The agent must operate on the kind of platform companies actually run: Kubernetes. It will read pod status and events, and later restart or roll back deployments, all under tight permissions. Everything has to keep fitting on a 16 GB laptop, and the Docker Compose setup must keep working for quick development.

## Decision

- **k3d** (k3s in Docker) with **one server node, no agents**, Traefik, ServiceLB and the k3d load balancer disabled. Image pinned to `rancher/k3s:v1.37.2-k3s1`, the same minor version as `kubectl`, to stay within the supported version skew.
- **Same host ports as Compose** (8001–8003, 9090, 3100, 3000) through NodePorts mapped by k3d to `127.0.0.1` only. `scripts/smoke.sh` and `scripts/smoke-obs.sh` work unchanged on both runtimes.
- **Split of responsibilities:**
  - **Terraform** (`infra/terraform`, `hashicorp/kubernetes` provider) owns the *platform*: namespaces, ResourceQuotas, LimitRanges, ServiceAccounts, RBAC and Secrets.
  - **Kustomize** (`deploy/k8s`) owns the *workloads*: Deployments, StatefulSet, Services, ConfigMaps.
  This mirrors how platform and application teams usually divide work, and keeps a fast `kubectl apply -k` loop for app changes.
- **Passwords generated by Terraform** (`random_password`) and stored only in Kubernetes Secrets and the git-ignored local state. Nobody types or reads them. (A shared team would use a remote, encrypted state backend.)
- **Least privilege per component:** Prometheus may list pods in `shop` and read `nodes/metrics` (never `nodes/proxy`, which would allow exec through the kubelet); Alloy may read pods and `pods/log` in `shop`; the agent's `centinela-agent` ServiceAccount is **read-only** on `shop` and has **no access to Secrets**. Write actions get a separate, narrow Role in Phase 7. Shop pods don't mount a ServiceAccount token at all.
- **Pod Security Standards `restricted`** enforced on every namespace: non-root users, no privilege escalation, all capabilities dropped, `RuntimeDefault` seccomp. Our own image also runs with a read-only root filesystem.
- **Quotas as blast-radius limits:** memory quotas per namespace (`shop` 1.5 GiB, `observability` 1.75 GiB, `centinela` 512 MiB) so a chaos experiment or a runaway agent cannot starve the laptop.
- **Observability inside the cluster** reuses the Compose configuration files through Kustomize `configMapGenerator`; only Prometheus (Kubernetes service discovery + kubelet cAdvisor metrics) and Alloy (logs through the Kubernetes API, no Docker socket) have `*-k8s` variants. Labels (`job`, `service`, `level`) are identical, so alert rules and the dashboard are shared.
- **Images reach the cluster with `k3d image import`**, no registry needed locally.

## Consequences

- `./scripts/k8s.sh up` builds everything from zero in a few minutes; `stop`/`start` pause the cluster to free RAM between sessions.
- WSL memory cap raised from 6 GB to 8 GB (ADR-0002). Expected peak: k3s ~0.6 GB + shop ~0.25 GB + observability ~0.4 GB.
- Prometheus and Loki use `emptyDir` storage: data is lost when their pods restart. Acceptable locally; incident history (Phase 5) will live in its own store.
- Container image versions are pinned in both `compose.yaml` and the Kubernetes manifests; Dependabot only updates the Compose side, so bumps must be mirrored by hand for now.
- **Lesson: CPU throttling.** On the first start Grafana 13 stayed "not ready" for 9 minutes. Its cgroup showed `nr_throttled` in **98% of periods** (498 s throttled) with a 0.5 CPU limit, and 237 MiB of real memory against a 384 MiB limit. Grafana now gets `cpu: 2` / `memory: 512Mi` (`GOMEMLIMIT=400MiB`): it bursts at startup and idles near zero afterwards. CPU limits trade latency for isolation; the memory quota remains the hard safety net.
- **Lesson: the same trap, now with Alloy.** After a second `k8s.sh up` in a row, Alloy stayed "not ready" and the script timed out. Evidence from its cgroup: **64% of CPU periods throttled** (1,819 s in total) with a 0.25 CPU limit, a working set of **188 MiB against a 192 MiB limit**, and **97% of its CPU time spent in the kernel** (`system_usec` 493 s vs `user_usec` 14 s): the kernel was constantly reclaiming memory, which burned the little CPU it had, so `/-/ready` missed its 1-second probe timeout. Every rollout of the shop makes Alloy open new log streams and re-read logs from the start. Alloy now gets `cpu: 1` / `memory: 384Mi` with `GOMEMLIMIT=300MiB` and a 3-second probe timeout; the `observability` quota grows from 1792 MiB to 2 GiB so a Grafana rolling update still fits. Rule of thumb confirmed twice: **size Go components by their real working set plus headroom, and look at `cpu.stat` before guessing.**
